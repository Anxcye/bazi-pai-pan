# 八字相关开源库调研整理

## 目的

这份文档用于整理当前调研过的几个八字/命理相关开源项目，帮助项目后续选型。

当前重点比较对象：

- `lunar-javascript`
- `mystilight-8char`
- `cantian-ai/bazi-mcp`
- `ChesterRa/mingpan`

本项目自身目标前提：

- 前端本地计算优先
- 核心能力聚焦八字，不做大而全命理平台
- 需要支持公历 / 农历输入
- 需要支持四柱、藏干、十神、五行、大运、流年、流月、流日、流时
- 规则要尽量可配置，尤其是换日等边界口径
- v1 不做解释文案，不做合婚

---

## 结论先行

### 总体判断

- 如果只求**最快做出完整结果**：`mystilight-8char` 最快。
- 如果想要**更规整的八字服务层思路**：`bazi-mcp` 更值得参考。
- 如果想要**更适合长期拆用、重组、沉淀为项目内核的结构**：`mingpan` 最值得深挖。
- 如果想要**最轻的基础历法能力**：`lunar-javascript` 依然是基础候选，但它本身不够覆盖完整项目目标。

### 当前推荐顺序

1. **`mingpan`**：最值得深挖其八字部分的 core / service 设计。
2. **`bazi-mcp`**：适合参考其结构化输出和规则参数设计。
3. **`mystilight-8char`**：适合快速 PoC，但不建议直接绑定为长期内核。
4. **`lunar-javascript`**：适合做基础历法能力，不适合单独承担完整产品能力。

### 推荐策略

**不要直接把任何一个外部库的原始输出结构暴露给 UI。**

更稳妥的做法是：

- 项目自己定义统一领域模型
- 外部库只作为底层算法或参考实现
- 通过 adapter 把外部结果映射到本项目自己的结构
- 用自己的标准样例做交叉验证

## 开源许可整理

### 各项目许可一览

| 项目 | 许可 | 商用可行性 | 需要注意的点 |
| --- | --- | --- | --- |
| `lunar-javascript` | 宽松开源许可（需以仓库实际版本 LICENSE 为准） | 通常可行 | 发布时应保留原许可文本与归属信息 |
| `mystilight-8char` | ISC | 通常可行 | 若复制/修改源码再分发，需保留版权与许可声明 |
| `cantian-ai/bazi-mcp` | ISC | 通常可行 | 同上；如果直接复用源码或分发修改版，要保留原许可 |
| `ChesterRa/mingpan` | Apache-2.0 | 通常可行 | 需要保留许可文本；修改后再分发时应标注改动；注意 NOTICE / attribution 要求 |

### 许可层面的实务结论

#### ISC

`mystilight-8char` 和 `bazi-mcp` 使用的是 **ISC License**。

它的特点：

- 宽松
- 可商用
- 可修改
- 可闭源集成
- 一般不会要求你的整个项目开源

需要做的主要事情：

- 保留原版权声明
- 保留许可文本
- 如果拷贝源码、修改源码、再分发，不能把原许可去掉

#### Apache-2.0

`mingpan` 使用的是 **Apache License 2.0**。

它同样属于宽松开源许可，但比 ISC / MIT 更正式一些：

- 可商用
- 可修改
- 可闭源集成
- 不会像 GPL 那样要求你的整个项目开源
- 包含更明确的专利授权条款

需要注意的事情：

- 保留 License 文本
- 修改源码后再分发时，应明确标注你改过哪些文件
- 若项目包含 `NOTICE` 文件，分发时要按 Apache 2.0 要求保留相关归属说明

### 对本项目的许可建议

无论最终选哪条技术路线，项目里都建议统一做这几件事：

1. 在仓库中保留第三方依赖许可清单
2. 如果复制外部项目源码进入本仓库，保留对应 LICENSE 和来源说明
3. 如果只通过 npm 依赖使用，也建议在文档中记录主要第三方内核来源
4. 产品上线时，在 about / legal / 开源说明页面中补充第三方组件许可信息

### 额外提醒：许可不是唯一风险点

这些库在**许可层面**大多问题不大，但命理类产品还有另一层风险：

- 结果准确性争议
- 不同流派口径不一致
- 用户把结果当成决策依据
- 某些解释性内容引发投诉

所以应把两件事分开看：

1. **开源许可是否允许使用**
2. **产品内容是否需要免责声明和边界约束**

建议产品层至少保留：

- 结果仅供参考
- 不构成专业意见或决策建议
- 不保证与所有流派或平台结果完全一致

## 1. `lunar-javascript`

### 定位

传统历法 / 干支 / 农历换算基础库。

### 优点

- 生态里较常见，很多项目都在用
- 对公历转农历、节气、八字基础获取比较方便
- 接入成本低
- 适合做四柱、节气、流日流时等基础能力的底层支撑
- 体量相对可控

### 缺点

- 更像基础历法工具，不是完整的八字产品引擎
- 需要自己补大量产品层逻辑
- 规则配置、领域结构、结果标准化，都要自己做
- 如果项目目标是“很快做出专业排盘软件感”，单靠它会比较慢

### 适合本项目的用法

- 用作基础历法能力
- 不直接当完整产品引擎
- 适合自己搭 domain 层时作为低层依赖

### 结论

**适合做底层，不适合单独承担完整项目。**

## 2. `mystilight-8char`

GitHub: `mystilight/mystilight-8char`

### 许可

- **ISC License**
- 属于宽松许可，商用通常没有大问题
- 若复制或修改源码再分发，需要保留许可声明

### 定位

一个功能很多、返回结果很丰富的八字排盘库。

### 优点

- npm 包可直接使用
- API 直接，上手快
- 返回内容很多：
  - 四柱
  - 藏干
  - 十神
  - 五行力量
  - 大运 / 流年 / 流月 / 流日
  - 神煞
  - 命宫 / 身宫
  - 各类分析字段
- 适合快速做出“结果很满”的原型

### 缺点

- 黑盒感较强
- 不是很适合做长期可控内核
- 返回里混有大量超出本项目 v1 范围的内容，例如：
  - 性格分析
  - 家庭背景
  - 外貌相关
  - 解释性内容
- 规则配置能力不够透明
- 测试覆盖有，但不像严格边界工程库那样让人放心
- 仓库规模和社区验证程度还不算强

### 对本项目的价值

- 非常适合快速 PoC
- 适合用来对照别的实现，看输出结构和常见字段
- 不适合直接把它的输出结构当项目内部标准

### 推荐接法

- 作为候选算法引擎之一
- 只抽取本项目需要的字段
- UI 不直接依赖它的原始输出格式
- 所有输出都走 adapter

### 结论

**适合加速原型，不适合直接当唯一长期内核。**

## 3. `cantian-ai/bazi-mcp`

GitHub: `cantian-ai/bazi-mcp`

### 许可

- **ISC License**
- 商用通常问题不大

### 定位

一个面向 AI / MCP 的八字服务。

### 技术特点

- 基于 MCP server 设计
- 使用：
  - `tyme4ts`
  - `cantian-tymext`
  - `@modelcontextprotocol/sdk`
- 输出是结构化的中文键名结果

### 优点

- 数据结构相对规整
- 输出内容比较像“结构化排盘结果”，不是纯文本胡说
- 明确暴露了一个重要规则参数：
  - `eightCharProviderSect`
  - 可控制 23:00-23:59 这段时间的换日口径
- 支持公历 / 农历输入
- 支持八字反推阳历时间
- 更像“清晰的服务层封装”而不是超级大黑盒

### 缺点

- 本质是 MCP 服务，不是前端直用的小型 SDK
- 输出键名以中文为主，不适合作为项目内部稳定 schema
- 还是偏服务封装层，不是面向前端应用内核直接设计的
- 可拆用性有，但不如 `mingpan` 那样有完整内部模块体系

### 对本项目的价值

- 值得参考它的：
  - 输出结构设计
  - 规则参数设计
  - `tyme4ts` 路线
- 如果未来项目接受“服务端 / MCP 计算”，它很有参考价值
- 如果坚持前端本地优先，则更适合拿来借思路，而不是整体拿来用

### 结论

**比 `mystilight-8char` 更像可靠服务层，但不适合直接按 MCP 形态塞进前端项目。**

## 4. `ChesterRa/mingpan`

GitHub: `ChesterRa/mingpan`

### 许可

- **Apache License 2.0**
- 属于宽松许可，可商用
- 相较 ISC/MIT 更正式，附带较清晰的再分发和专利条款

### 定位

一个中华传统术数 MCP 平台，不仅包含八字，还包含：

- 紫微斗数
- 六爻
- 梅花易数
- 大六壬
- 奇门遁甲

### 为什么值得重点看

虽然它是 MCP 服务，但它内部并不只是简单包装，而是已经形成了比较完整的工程结构：

- `src/core/bazi/*`
- `src/services/bazi/*`
- `src/core/calendar/*`
- `src/services/bazi/calculators/*`
- `src/services/bazi/analyzers/*`

这说明它不只是“服务壳”，而是有潜力作为领域内核参考。

### 优点

- 八字相关结构分层清楚
- 有 core / service / calculator / analyzer 拆分
- 功能覆盖与本项目目标高度接近：
  - 四柱
  - 藏干
  - 十神
  - 五行
  - 大运
  - 流年
  - 流月
  - 流日
- 支持真太阳时校正（通过经度）
- 代码组织比前两个候选更像可长期演进的项目
- 更适合拆用、借设计、提炼成自己的内核

### 缺点

- 体量大，不只是八字项目
- 带了很多本项目暂时不需要的术数模块
- 仍然是 MCP-first 项目，对外形态不是前端 SDK
- 内部分析能力很多，容易超出本项目 v1 范围
- 代码野心较大，未必所有模块都已经收敛到稳定状态

### 对本项目的价值

- 很适合深挖它的八字 core / service 设计
- 很适合借它的分层方式与领域模型组织
- 很适合把其中八字相关最小子集拆出来做本项目内核参考
- 不建议整仓整体引入

### 结论

**目前最值得深挖的候选。适合借结构、借模块、借分层，不建议整包照搬。**

## 面向本项目的建议

### 最不建议做的事

- 直接把某个库的输出结构绑定到 UI
- 直接把大型 MCP 项目整体搬进前端项目
- 在没有自家样例验证前，默认外部库就是“标准答案”

### 最推荐做的事

1. **项目自己先定义统一领域模型**
   - 输入模型
   - 四柱结果模型
   - 流运模型
   - 规则配置模型

2. **用 adapter 接外部实现**
   - `adapter/mystilight`
   - `adapter/bazi-mcp-style`
   - `adapter/mingpan-style`

3. **建立标准验证样例**
   - 普通样例
   - 节气边界样例
   - 23:00 换日边界样例
   - 闰月样例
   - 未知时辰样例

4. **把 v1 范围收紧**
   - 先只做结构化排盘
   - 不引入解释性分析
   - 不展示高风险判断类字段

## 当前推荐路线

### 路线 A：最快出结果

- 先用 `mystilight-8char` 做 PoC
- 很快把结果页面跑起来
- 再逐步替换成自己的 adapter 和结构

### 路线 B：中期更稳

- 深挖 `bazi-mcp` 和 `mingpan`
- 重点研究：
  - 边界规则如何设计
  - 四柱和流运结构如何组织
  - 真太阳时和换日配置如何建模

### 路线 C：长期最稳

- 用 `lunar-javascript` + 自研领域模型作为底层
- 参考 `mingpan` 的八字模块结构组织项目
- 逐步只吸收需要的能力，不把外部项目整体引入

## 目前建议的实际执行策略

如果要继续推进本项目，当前最稳的动作顺序是：

1. 先整理一组标准出生样例与期望结果
2. 用这些样例同时验证：
   - `lunar-javascript` 路线
   - `mystilight-8char`
   - `bazi-mcp`
   - `mingpan`（仅八字部分）
3. 先决定：
   - v1 是“先快”还是“先稳”
4. 无论选哪条路线，都先实现统一 adapter 层

## 当前阶段的建议结论

如果下一步只选一个方向继续深挖：

**优先深挖 `mingpan` 的八字部分。**

理由：

- 它最像可以被拆解、吸收、重组的工程化实现
- 它的功能覆盖最接近本项目目标
- 它在分层和模块组织上最有借鉴价值
- 即使最终不直接采用，也很适合当架构参考样本

如果只是想尽快验证结果页面和展示链路：

**可以先拿 `mystilight-8char` 做一次快速 adapter PoC。**
